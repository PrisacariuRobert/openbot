# OpenBot: product audit and alternative strategy

Audit date: 4 September 2026. Baseline: 0.28.0, commit `88b8de9`. Remediation: **0.29.0 development branch**, not a published release.

Follow-up, 5 September 2026: 0.34 adds a genuine SwiftUI/AppKit macOS client with native conversations, search, replies/reactions, workspace files, teammate setup, Work, full supported automation editing, isolated-browser takeover, visible skill teaching, Live Studio, approvals, and crash-recovery decisions; it does not embed the web app. 0.33's durable action ledger, 0.32's native source-backed jobs, 0.31's reports and commit-bound code checks, and 0.30's execution/usage safeguards remain in place. See [current desktop validation](QA_0.34.md). This closes the native Mac client gap; it does not create zero-setup signed distribution, a bundled runner, Windows support, universal provider-level exactly-once behavior, the two-model repeated acceptance gate, physical-device/cellular validation, or the remaining isolation milestones.

Follow-up, 7 September 2026: artifacts are first-class objects (studio-wide index with per-artifact revision history on web, Mac and API), and the studio can now **extend itself**: when a teammate hits a capability it does not have, it may propose writing one small tool in its own private workspace via a new `self_extend` tool. The proposal always pauses for the owner's exact review (capability, plan, tool-file effect) in the existing approvals UI; approving restarts the same task with the owner's chosen coding model (Control center → Permissions & usage → Self-extending studio, default on, per-run `model_override` validated against the teammate's own connection, safe fallback to its own model). Evidence is transport-level only: unit tests for the review/settings/workspace generation, plus a fixture-server test proving the approve→override→continuation path and the non-belonging-model fallback. No live-model run has yet proposed or completed a self-built tool, and newly written tools are only as sandboxed as the bot workspace itself. This is an OpenBot-only differentiator to prove, not a parity claim.

Same-day follow-up: memory retrieval is no longer keyword-only. The owner can now choose an embeddings connection (key-based or local OpenAI-compatible endpoint, e.g. an OpenAI key, OpenRouter, or a local server) in Control center → Permissions & usage → Memory with meaning. Saving the choice probes the endpoint live and refuses to save on failure; `memory_search` then blends meaning similarity (60%) with the existing keyword score (40%), caching one vector per note and re-embedding only new or edited notes in a single batched call. Anything unreachable falls back to exactly today's keyword ranking, and the tool result says which method was used. Evidence is transport-level: unit tests for resolution/client/blend, an in-process test proving a paraphrase with zero shared words is recalled and vectors are cached then invalidated on edit/forget, and a fixture-server test proving the save probe accepts a working endpoint and rolls back a failing one. No live-model recall comparison has been measured yet.

Same-day follow-up: teamwork is now visible and steerable. Handoffs and teammate questions used to happen privately with only a past-six signal list and a "consulting" status; the owner can now see every live delegation (who is paused waiting on whom, the original request, each consultant's run status, how long it has waited, and a stuck badge when all consultant work finished without reviving the waiter) at the top of Control center → Team signals, and can **recall** a delegation: the consultant work is stopped and the coordinator resumes immediately with the owner's instruction to finish from what it knows. Evidence is behavioral at fixture level: a database test for the delegation listing and a fixture-server test proving recall stops the consultant, resumes the coordinator with the recall prompt, records the activity, and refuses a second recall. The runner's own resume path cannot double-fire after a recall because the resumed run leaves the waiting state atomically. No live multi-teammate wait has been steered yet.

Same-day follow-up: teammate governance exists. There was previously no way to remove a teammate and no limit on creation; now teammates **retire** instead of being deleted: history (conversations, runs, receipts) is preserved, they leave the roster, their active work is stopped, and they cannot receive handoffs, questions, or new runs until restored. A studio-wide **seat cap** (default 12, adjustable 1–100 in Control center → Teammates) is enforced on creation, duplication, and restore, with grandfathering when the limit is lowered. The owner retires from the teammate panel, sees seat usage and retired teammates with one-click restore in Control center, and gets plain 409 explanations at the cap. Evidence: database tests for cap/retire/restore/exclusion/run-blocking, plus a fixture-server test for the retire/restore/duplicate-at-cap HTTP paths. No live studio has yet hit the cap or retired a working teammate.

Same-day follow-up: first-run setup is now guided instead of implied. A new `GET /api/readiness` endpoint reports the three setup steps with live detail (model runtime from the cached provider scan, connected AI connections, teammate count), and Control center shows a "Get set up" checklist only while anything is incomplete, with one-tap actions into AI connections or teammate creation. The main Studio's first-teammate empty state and the scripted onboarding test already covered the creation flow; this closes the "what am I missing" gap around it. Evidence: a fixture-server test for the endpoint shape and teammate tracking, plus a screenshot against a retired-roster fixture showing real host runtime/connection state. Deliberately out of scope here, stated plainly: Apple signing/notarization, Gatekeeper delivery proof, and Windows support cannot be produced from this checkout and remain the actual zero-setup blockers.

Same-day follow-up: YOLO mode exists for owners who want no pauses. A new studio setting (Control center → YOLO mode, off by default, explicit confirm on enable) auto-decides every fresh approval exactly as if the owner had instantly approved it: tool-action pauses, task-start reviews, and scheduled-automation starts. The design is deliberately narrow: the full review, fingerprint check, execution path and ledger stay intact (reviews that cannot be approved stay pending), sign-ins still need their human, and access grants are untouched — YOLO skips reviews, never permissions. Every auto-decision is recorded with an "Auto-approved by YOLO mode" activity. Evidence: a fixture-server test proving a spend-flagged task pauses with YOLO off, auto-approves with a ledger entry with YOLO on, and pauses again after switching off. Live, high-stakes use (real sends/publishes under YOLO) has not been exercised.

Same-day follow-up, cross-platform direction (owner request, inspired by t3code): T3 Code ships one owner-hosted server with an Electron desktop app, native iOS/Android apps and a web app over the same API, plus a relay for remote access and winget/brew/AUR packaging. OpenBot already has the same core shape (owner-hosted server + same-UI web client + `setup.sh --relay` + native Mac/iOS + headless linux-x64/win-x64 bundles), so the t3code model fits without an architecture change. The missing pieces are thin shells: a Windows/Linux desktop wrapper around the existing web client (Electron or Tauri — same look, one codebase), an Android answer (PWA first, native later if the platform matters), and registry packaging (winget/brew/AUR) after the signed release. SwiftUI does not port, which is exactly why the shared web client is the cross-platform layer; the native Mac/iOS apps stay the premium tier. Sequencing: after the beta release and the Work Receipt (P1) — not before.

Same-day follow-up, sign-in handoff hardening (owner hit Google's bot wall): completing a private sign-in inside the headless takeover browser gets refused by providers — Google shows "This browser or app may not be secure." Two fixes landed. First, sign-in handoffs now automatically relaunch that teammate's browser as a **visible Chrome window** on the host (same persistent profile, resuming the current page or the sign-in origin after a restart): `BrowserManager.ensureHeaded` runs when a sign-in is requested and whenever the private takeover screen is opened; display-less hosts keep the headless fallback. Owner and viewer drive the same browser either way. Second, the takeover screen is no longer a frozen picture: it shows a "Live screen — click directly on the page" pill, crosshair cursor, and refreshes every 3 seconds while open. Remaining honest limits: providers can still refuse sign-in from automation (passkeys, some SSO) — the visible window is the practical path, not a guaranteed bypass.

Same-day follow-up, Google bot-wall root cause (owner still blocked in the headed window): the refusal was our fingerprint, not Google being absolute — Playwright-launched Chrome exposes `navigator.webdriver = true`, the exact signal Google's sign-in checks. Fix: both browser launches pass `--disable-blink-features=AutomationControlled` (the documented, still-working 2026 remedy; verified locally: webdriver true → false with the flag), and `ensureHeaded` now relaunches a headed window that was started by an older build (launch-args version marker) so retries pick the fix up without a restart. Remaining fallback if a provider still blocks (cookies pinning a refused attempt): a "sign in with your own browser" bridge — open the sign-in page in the owner's normal browser, then import the session cookies into the teammate's private profile (needs one Keychain approval; Chrome must not be running when its cookie store is copied). Not built yet.

The CTA is a primary "Open the private browser" button. Input ops are queued fire-and-forget (the stream shows the result), with a slow screenshot-poll fallback while no stream is running. Same-day follow-up, professional sign-in pattern research (owner asked how OpenAI does it): OpenAI's shipped pattern across Operator → ChatGPT agent → ChatGPT Work/cloud browser (Atlas folded in Aug 2026) has five pillars. (1) The agent never owns credentials: at a login wall it pauses and asks the owner to take over the browser; during takeover screenshot capture is suspended so nothing entered is seen or collected. (2) The newer cloud-browser flow adds a secure sign-in form in the app UI, preceded by a review model that checks the sign-in request for phishing; credentials go directly to the remote browser, are invisible to the model and are not stored. (3) Sessions persist per site (sign in once per site) and can be cleared per site or wholesale in settings. (4) Per-site access permissions (always ask / auto-approve / always allow, per-site overrides) are separate from approval for consequential actions. (5) Sensitive sites force watch mode, and consequential actions still require confirmation. OpenBot already matches the core: pause-and-handoff approvals, a live private in-app browser with direct input, credentials never in chat/model, persistent per-bot cookie profiles, and per-site access gates; being local-first, our direct-typing pane is privacy-equivalent to OpenAI's secure form (their form exists because their browser runs in their cloud). Gaps worth adopting, in order: (a) a per-site "sign out & clear this site's data" control (OpenAI's data controls); (b) automatic phishing/reputation review of a sign-in request before showing the handoff (OpenAI's review model); (c) the own-browser cookie bridge from the previous entry as the reliable fallback when a provider refuses automation; (d) explicit "screenshots suspended during takeover" language — the model is paused while `awaiting_approval` today, but this should be stated and enforced where model-visible browser views are served. Sources: OpenAI help center (ChatGPT agent 11752874, cloud browser 20001280), Introducing Operator/ChatGPT agent.

Competitor study, Hermes (NousResearch) — hermes-agent (243k stars, 32.7k commits) and Hermes-Bot-Mode (659 stars, archived Aug 2026: bundled into Desktop as a default-on plugin at `apps/desktop/src/plugins/hermes-bots/`). What Bot Mode is: a roster UI over the existing "profile" primitive — one bot = `~/.hermes/profiles/<name>/` (isolated config, memory, skills, credentials, history). Shipped pieces: roster pane with avatars/preview; "Active now" presence strip (bots that wrote within 90s; never reorders the roster); New/Edit agent with clone, model pin, custom SOUL.md, per-skill/per-toolset enablement; roster groups; group chats (2-6 bots, up to 3 serial rounds, 10 messages per turn, silence settles the room, @name pulls a bot in, @user escalates to the owner with a "needs you" badge, persistent `Group: <name>` session per bot); bot-to-bot messaging as CLI handoffs with attribution; @mentions in any chat; routines per bot over shared cron; avatars incl. pets that bounce while the bot is busy. What the core agent is: Python CLI/TUI + messaging gateway (Telegram/Discord/Slack/WhatsApp/Signal/Email), self-improving skills loop (autonomous skill creation after complex tasks, skills self-improve during use, memory nudges), FTS5 session search with LLM summarization, Honcho user modeling, cron, subagents, 7 terminal backends (local/Docker/SSH/Singularity/Modal/Daytona/Vercel with serverless hibernate), agentskills.io open standard, research trajectory tooling, OpenClaw migration command, Nous Portal subscription bundling models+tools. No real browser automation of its own (cloud browser comes from the Portal's Browser Use tool gateway — remote, cannot sign in to sites reliably). OpenBot comparison — parity or better: named bots with per-bot credentials/browser/memory (equivalent isolation), group threads with mention routing and membership notes, consultations (attributed bot-to-bot), routines with connector-readiness gates (stricter than Hermes cron), skills incl. taught drafts + community skills, embeddings memory retrieval, native macOS/iOS + web + Electron + relay (Hermes has CLI/TUI/Desktop/messaging only), approval ledger + Work Receipt (no Hermes equivalent), per-bot live browser with owner sign-in takeover (strictly stronger than any Hermes path), signed one-bundle distribution. Inspiration worth taking, in order: (1) the group-chat discipline — hard caps (3 rounds/10 messages), silence-settle, @user escalation with a visible "needs you" badge; (2) presence strip "Active now" above the roster that never reorders; (3) per-skill and per-tool enablement per bot surfaced in the profile editor; (4) skills from completed runs: propose a draft skill (approval-gated, Work-Receipt-backed) instead of Hermes's unconditional self-improvement loop; (5) an import command for Hermes/OpenClaw profiles (SOUL.md → instructions, memories, skills) to capture their 243k-star ecosystem; (6) explicit agentskills.io compatibility as a distribution channel. Do NOT adopt: unconditional autonomous skill/memory mutation (conflicts with OpenBot's approval model), remote-serverless browser environments (OpenBot's identity is "your computer"), and Nous Portal bundling (OpenBot is bring-your-own-keys by design — state it as a differentiator). Stand-out strategy: Hermes proves the roster concept is now table stakes in open source; OpenBot wins on provable work (receipts), the private real browser with owner takeover, native apps, and the trust model — market against "the team that shows its work," and make the first-run import from Hermes a growth lever.

Same-day follow-up, own-browser cookie bridge shipped (roadmap item A1; the guaranteed sign-in fallback): "Provider refuses this browser? Sign in with your own Chrome instead" on the private sign-in pane opens a three-step bridge. Step 1 `POST /api/approvals/:id/own-browser {action:"open"}` opens the sign-in origin in the owner's real Chrome via `open -a "Google Chrome"` (deliberately Chrome, not the default browser — only its cookie store can be imported; only macOS today). Step 2 the owner signs in there and quits Chrome (Cmd+Q) so the cookie store is flushed. Step 3 `{action:"import"}` resolves the owner's Chrome profile from `Local State`, copies the Cookies store (plus its WAL so un-checkpointed sign-ins are included) to a temp file, decrypts cookies in-process with the Keychain "Chrome Safe Storage" key (`security find-generic-password`; the owner sees one Keychain approval prompt the first time), filters to cookies that apply to the sign-in host only (RFC-6265 domain-match, bare public suffixes rejected), installs them into the teammate's persistent Playwright profile (`BrowserManager.importOwnerCookies`), reloads the page at the origin so the signed-in state is visible, and deletes the copy. Cookie values are never logged, displayed or seen by the model; bridge errors carry instructions, never cookie material. Correctness details found by test: Chrome's 1601-epoch microsecond timestamps exceed JS's safe integer range for real 2026+ dates (CAST to TEXT for reads, BigInt in fixtures), and a dot-form host cookie covers its own host (RFC 6265 domain-match). 5 new fixture tests (`own-browser-bridge.test.ts`: v10 decryption round-trip, host matching incl. suffix rejection, epoch conversion, Local State profile resolution, full store read with encryption/decryption/unrelated-cookie exclusion). Suite 547 tests, 538 pass — the same 8 pre-existing web-redesign failures (roadmap D1). Not yet exercised live: the real Keychain prompt and a real Google import need the owner's Chrome; the honest limit stays that providers can still refuse the imported session in rare risk checks.

## What Grok Bot actually offers

Cursor documents a managed persistent computer, cloud routines, messaging and steering, skills, artifacts, plugin references, and parallel work. Bots within an account share its computer and sign-ins; per-bot screens are not separate security boundaries. Its main advantage is having these parts operated together for the user. OpenBot has related primitives, but assembling and maintaining them is still the owner's job. [Work with Grok Bot](https://cursor.com/docs/grok-bot/work).

Its published use cases center on source-backed deliverables: operational digests, expense reconciliation, research, and bug reproduction, with consequential changes reviewed. That is a better comparison target than avatar similarity or a connector count. [Grok Bot use cases](https://cursor.com/docs/grok-bot/use-cases).

Enterprise adds identity and policy administration that this single-owner application does not implement. These controls are not all available on every Cursor plan. [Teams and Enterprise](https://cursor.com/docs/grok-bot/teams).

Individual users describe useful recurring inbox/calendar summaries, invoice filing, research and alerts, but also consumption limits. Other reports describe timeouts, forgotten work and formulaic writing. These are **anecdotes, not measured failure rates**; they suggest test cases, not grounds to declare OpenBot better. ### High-risk boundaries still open

- Host model processes can inherit runtime-level configuration, plugins and account access. Internal tool tokens are now scoped to one run and teammate, and named-agent tool policies are verified against the real runtime. These controls and per-bot workspaces do **not** constitute a complete process/credential sandbox.
- Bot Docker terminals retain outbound network access. Command-word detection cannot reliably classify arbitrary programs. Do not promise that every possible external write is intercepted.
- Browser URL validation is lexical, not a full DNS-resolution/redirect/subresource egress policy. Loopback is intentionally permitted. Private-network isolation needs dedicated enforcement and adversarial tests.
- Browser approval fingerprints detect changed URL/control metadata, not arbitrary changes in nearby form data or all page scripts. Old approvals without a fingerprint now require renewed inspection.
- 0.30 adds active-time, idle, step, output and reported-token enforcement. 0.35 shares the job allowance across consultants and steered follow-ups. Usage is checkpointed while running; unreported in-flight usage can still overshoot, so neither limit is an exact billing guarantee. 0.33 records and single-claims approved actions, then stops for human reconciliation after an interrupted remote call. This prevents blind local replay but is not provider-level exactly-once delivery; automatic reconciliation still needs a stable provider identifier or safe lookup contract.
- Coding checks now pass real independent JavaScript and Python bug-fix fixtures in network-disabled disposable Linux views, preserving the original checkout and test oracle. This does not establish arbitrary dependency provisioning, native/mobile builds, large repositories, or semantic test quality.

These are blockers to advertising unattended, unrestricted computer autonomy. Expanding permissions would hide the gap, not close it.

## Different in useful ways

These are design advantages to prove, not performance wins already measured:

1. **Portable ownership:** move data and readable, versioned skills between machines without moving to a proprietary service. Include tested recovery and clear export contents.
2. **Model choice with honest cost:** mix local, API and permitted subscription runtimes; show capabilities and measured usage. Never silently fall back to a paid model or pool somebody else's account.
3. **One answer, inspectable work:** private consultation, linked sources, files and actual tool outcomes. Technical internals can be collapsed; history must not be rewritten.
4. **Scoped access instead of one shared account soup:** separate browser profiles and explicit app/project grants. Complete the runtime/egress boundary before claiming security isolation.
5. **Recoverable actions:** preview changes, retain revisions, single-claim approved work, and ask the owner to reconcile uncertain external results. Next add provider-specific automatic reconciliation where a stable remote identifier exists. A trustworthy stop/resume is more valuable than another integration logo.

OpenCode's provider documentation distinguishes account credentials from provider configuration and describes local/compatible endpoints; OpenBot now reflects that distinction rather than equating a key with an integration. [OpenCode providers](https://opencode.ai/docs/providers/).

The supplied `t3code/docs/internals/providers.md` offers a useful architectural reference: validated runtime drivers, instance registries and event ingestion rather than provider-specific branches throughout orchestration. Adopt that separation incrementally; do not import its product wholesale.

Hermes' computer-use documentation suggests a next research track: application-scoped observations, numbered targets and bounded screenshot retention. Its backend and platform constraints are explicit. OpenBot should adopt the discipline of observe → act → verify, not just add a screenshot button. [Hermes computer use](https://hermes-agent.nousresearch.com/docs/user-guide/features/computer-use).

## Design direction

Calm work surface, playful teammates. Warm neutral canvas, readable graphite text, one restrained violet action colour, consistent 8/12/16/24 spacing and hairline separation. Animation belongs to small independently moving characters, not every card. Preserve colour controls, blinks, expression states and reduced-motion support.

Use three primary destinations: **Conversations**, **Work**, **Settings**. Keep model setup, host maintenance and permissions out of the everyday message flow. Prefer a clear result card to an oversized chat bubble full of process narration. Avoid sales slogans and gradient hero banners inside settings. Show one useful next action for each error; put technical detail behind disclosure without hiding the original failure.

The new connection panel is the first reference implementation: grouped account rows, API/local setup, real provider marks, explicit saved status, restrained mascot, accessible fields and mobile containment. This is **not** a claim that every existing web/native screen has been redesigned.
