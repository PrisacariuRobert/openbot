# Capability coverage — off-screen release review

This document deliberately stays **outside** the film. User direction is to prepare the introduction ahead of the finished release without covering it in roadmap badges. The film shows the intended product experience; it must not be described as independent performance proof or a production screen recording.

| In the film | What must be true at publication |
| --- | --- |
| Teammate consultation and one shared answer | Representative multi-teammate jobs complete with the lead retaining responsibility; no duplicate finals or fabricated consultation. |
| User-chosen providers/subscriptions/API/local models | Each named path is tested against current authentication and account terms. A saved sign-in is not working model access; OpenBot supplies no subscription allowance. |
| Signed-in private browsers | Manual login, pause/resume, expiry and private text handling work in representative services. This is not universal permission to every third-party app. |
| Email, calendar, files, Slack, Notion, GitHub | Real capabilities depend on connector/site, scopes, per-teammate grants and API availability. Logos alone are not an integration guarantee. |
| Mac apps and files | Owner scope and macOS permissions work on supported releases. Locked screens and inaccessible controls are handled honestly. |
| Documents, presentations and spreadsheets | Real outputs open in the intended apps and pass content/layout checks. The film's launch pack and charts are illustrative. |
| Project coding and tested pull requests | Worktree isolation, actual tests, reviewable changes and exact destination-bound publication proof are verified on real projects. A model's “done” is insufficient. |
| Routines | Time zone, weekday, daylight-saving, restart recovery and missed-run behavior are verified; external actions retain approval boundaries. |
| Approval and human control | Exact account, recipients, content and action are visible before sending; recovery cannot repeat uncertain writes. The film's approval changes by editorial timing, not a real send. |
| Mac and iPhone continuity | Physical-device and away-network pilots pass. Hosted relay, cellular, push and Apple signing are separate gates. This film is not evidence that away access is currently turnkey. |
| Skills/MCP, teaching, memory, research, voice | Tools and runtimes are supported; permissions/data boundaries are clear; memory is user-controlled; voice availability is tested. It does not mean every Hermes or competitor plugin runs. |
| Self-extending studio | Approval field validation and same-task coding-model override have unit/fixture coverage. The configured model must belong to the teammate's connection; otherwise the existing model is retained. Writing exactly one `.opencode/tools/<name>.ts` file is currently a prompt instruction, not demonstrated hard filesystem enforcement. A completed live-model build, usable generated tool, safe file visibility/deletion and failure recovery must be verified before describing the scene as proven behavior. |
| Build → test → improve → use → reuse in the demo-led cut | The local parser fixture reproduces two failures, four passing cases after a manual source change and a €1,749.50 total. It does not prove an agent can autonomously generate, load, test, repair, invoke and later rediscover a new tool. That end-to-end cycle, bounded retries, honest failure reporting and permission preservation require live-model tests. This illustrates tool self-extension, not model-weight training or unlimited authority. |
| Open source and local-first | Ship matching source/license, installation instructions and dependency notices. Local-first does not mean remote model requests never leave the Mac. |

The [unlocked-Mac evidence](../../docs/QA_UNLOCKED_MAC_2026-09-07.md) records actual unit/build/fixture checks, synthetic free-model scenarios and bounded real Gmail/Drive reads. Its Google Calendar pilot is blocked by API configuration. Neither that evidence nor this animation establishes competitor parity.

This task changes the UI and creates the film. It does **not** complete every roadmap feature, enable public away access, install a physical phone app, sign/notarize a public installer, or publish marketing.

Before public use: reconcile each scene with the exact release, verify service marks/provider paths, run real-account and device/distribution pilots, and get the owner's final creative review. If the depicted experience is not available, publish only with clear surrounding concept/preview context or edit to the tested scope.
